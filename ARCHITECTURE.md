# PSA-NPIC Architecture

This is the current architecture guide for the PSA-NPIC monorepo. It records the system structure, module boundaries, API behavior, data flows, and implementation details that are easy to lose when changing one feature at a time. Verify time-sensitive details against the code before relying on them.

## Approach and boundaries

The system is a TypeScript modular monolith managed with pnpm and Turborepo. Keep feature boundaries clear, evolve the monolith as needs emerge, and extract services only when there is a concrete operational or ownership reason. The backend uses strong typing, OpenAPI contracts, and PostgreSQL as its source of truth. Avoid distributed infrastructure and patterns such as Kafka, microservices, or CQRS unless a feature explicitly requires them.

## Backend architecture

### Request lifecycle

```
Request
  → IdempotencyMiddleware  (POST/PATCH/PUT only; middleware runs before guards)
  → JwtAuthGuard          (global APP_GUARD #1)  ← skipped if @Public()
  → UserAwareThrottlerGuard (global APP_GUARD #2) — keys on req.user.id when JwtAuthGuard set one, else IP
  → ValidationPipe (whitelist + transform)
  → Handler
  → ResponseInterceptor  → { success, data, meta? }
  → GlobalExceptionFilter  (on throw)
```

JwtAuthGuard runs first specifically so the throttler can see `req.user` — a fairness fix for shared-NAT traffic (one busy office/campus no longer shares a single IP-keyed bucket). `UserAwareThrottlerGuard` (`common/guards/user-aware-throttler.guard.ts`) falls back to IP for anonymous/public requests, where `req.user` is never set.

### URL structure

Global prefix `api`, excluded for `GET /` and `GET /health`. URI versioning with `defaultVersion: '1'`.

- Root: `GET /` → `Hello World!` (no auth, no prefix)
- Health: `GET /health` (no auth, VERSION_NEUTRAL)
- All other routes: `/api/v1/<resource>/...`

### Auth model

- `@Public()` on a handler or controller class bypasses `JwtAuthGuard` entirely. Without it, a valid `Bearer` token is required.
- JWT payload is exactly `{ sub, role }` where `role` is `'user' | 'admin' | 'super_admin'`. `JwtStrategy.validate` (`src/auth/strategies/jwt.strategy.ts`) checks the DB, rejects soft-deleted users (`deletedAt` set), and sets `req.user` as `RequestUser { id, role }`. `super_admin` satisfies every `@Roles('admin', 'super_admin')` guard. The only current permission gradation: only `super_admin` can assign `admin`/`super_admin` roles (`AdminService.createUser`/`updateUser` throw `ForbiddenException` otherwise), and the Team page is super_admin-only.
- Use `@CurrentUser() user: RequestUser` to access the authenticated user in a handler.
- Dual tokens: short-lived `accessToken` (default 15 min) + long-lived `refreshToken` (default 30 d). `refreshToken` uses a separate `JWT_REFRESH_SECRET`.
- Soft-delete is enforced at all three entry points: `loginWithPassword`, `refresh`, and `JwtStrategy.validate`.

### Auth flow — phone registration & login (OTP + password)

```
POST /api/v1/auth/register   { phone }                        → sends OTP via Supabase (or dev bypass)
POST /api/v1/auth/otp/request { phone }                       → re-sends OTP (public; E.164-validated via RequestOtpDto)
POST /api/v1/auth/otp/login  { phone, password }              → login-mode: validates credentials, THEN sends OTP (unknown phone / wrong password → 401, no SMS)
POST /api/v1/auth/otp/verify { phone, token, password,
                              firstName?, lastName? }         → verifies OTP; creates the account (register) or logs in the existing user
```

`verifyPhoneOtp` is the single creation/login chokepoint. It looks up the active user by `primaryPhone` first:

- **User exists** — the submitted `password` must match (`bcrypt.compare`); mismatch → 401 **before** any OTP is consumed. The conflict path can never overwrite credentials: payload extras land only in the INSERT `.values()`, while `onConflictDoUpdate.set` stays `{updatedAt}` (locked by a unit test). Even a replayed body with a fresh password/names/username is ignored.
- **User absent or a legacy bare account** (null `passwordHash` — created before passwords were required) — the verify **completes the account in place**: bcrypt-hashes the password (10 rounds), stores `firstName`/`lastName`, and generates a unique username via `generateUniqueUsername(buildUsernameBase(first,last))` → `sokdara`, `sokdara2`, …. Names carry from the web register form; a phone-digit fallback is deliberately avoided so the nicer name-based handle stays free.
- Verify **without** `password` is a 400 — there is no passwordless login path (the public `otp/request` resend can never be a backdoor).

`mirrorSupabaseUser` in `auth.service.ts` upserts users without a Supabase-specific ID: phone auth conflicts on `primaryPhone`; social auth (Google/Facebook) conflicts on `email`. Both paths insert into `user_auth_providers` and `user_phones` (isPrimary: true) when a phone is present. Soft-deleted phones don't conflict (partial index with `WHERE deleted_at IS NULL`) — a fresh row is created with the extras.

### Database access

`DbModule` is `@Global()` — never import it in feature modules. Inject the typed Drizzle client with `@Inject(DRIZZLE) private readonly db: DbClient`. For raw SQL (e.g. health ping), inject `@Inject(PG_CLIENT) private readonly sql: postgres.Sql`.

Drizzle is configured with `casing: 'snake_case'`: write schema column names in camelCase; the driver maps to `snake_case` in the DB automatically.

Schema files live in `src/db/schema/` and are re-exported from `src/db/schema/index.ts`. Add new tables there.

### Supabase

`SupabaseModule` is `@Global()` — never import it in feature modules; inject `SupabaseService` directly. It exposes one admin client (service-role key) and a helper to create a user-scoped client. Auth (OTP, social OAuth, token validation) and storage operations go through `SupabaseService`.

`signInWithOtp` and `verifyOtp` support a dev bypass via `DEV_OTP_TOKEN` env var — when set, no SMS is sent and that fixed token is accepted. Keep the value at 6 digits or fewer — the web OTP input (`apps/web/components/auth/OtpVerifyForm.tsx`) has 6 single-digit boxes, so a longer token can never be entered. Currently `000000` in `apps/backend/.env`; changing it requires a backend restart. In dev, the Supabase-side fake user id is the literal string `'dev'`; the local `users.id` is DB-random (`defaultRandom`), and repeat-login identity is guaranteed by the `primaryPhone` upsert in `mirrorSupabaseUser`.

### Response envelope

`ResponseInterceptor` wraps all non-string handler return values:

```json
{ "success": true, "data": <value>, "meta": <pagination?> }
```

String return values pass through unwrapped (preserves `GET /` → `Hello World!`). Errors from `GlobalExceptionFilter` have shape `{ "success": false, "error": { "code", "message", "details?" } }`.

### Idempotency

`IdempotencyMiddleware` runs on POST/PATCH/PUT. Clients include an `Idempotency-Key` header. The middleware hashes the request body (SHA-256) and stores key+method+path+user in the `idempotency_keys` table (unique with `NULLS NOT DISTINCT` so anonymous requests dedupe too). Because middleware runs before guards, it verifies the `Bearer` token itself (via `JwtService`) to resolve the user; invalid/absent tokens are scoped as anonymous (`user_id NULL`). First-request detection uses `INSERT … ON CONFLICT DO NOTHING … RETURNING`: a returned row means "we own it, proceed"; a conflict means 422 (a different body hash, whatever the row's state), replay (completed), 409 (processing < 30 s), or reclaim (failed or stale-processing rows are flipped back to processing — conditionally on the `lockedAt` read, so two racing retries cannot both proceed). A 5xx response is recorded as `failed`, not cached, so the retry re-executes (2026-10-23).

### Categories i18n

Categories and subcategories use **four tables**, not two:

| Table                      | Purpose                                            |
| -------------------------- | -------------------------------------------------- |
| `categories`               | Structure only (slug, icon, sort_order, is_active) |
| `subcategories`            | Structure + `field_schema` JSONB                   |
| `category_translations`    | `(category_id, locale, name, description)`         |
| `subcategory_translations` | `(subcategory_id, locale, name, description)`      |

Supported locales: `'en' | 'km' | 'zh'` (the `localeEnum` pgEnum). Locale is resolved from the `Accept-Language` request header via `resolveLocale()` in `src/categories/locale.util.ts`.

`CategoriesService` uses **two aliased LEFT JOINs** per query (one for the requested locale, one for `'en'`), then COALESCE in JS:

```ts
name: row.reqName ?? row.enName ?? row.cat.slug; // slug is the last resort
```

**`field_schema` JSONB** stores a `FieldDef[]` array describing the listing creation form fields for that subcategory. The frontend is currently independent (hardcoded forms), so `field_schema` is present but not consumed at runtime. `FieldDef` type is defined in `src/db/schema/categories.schema.ts` — key, label (i18n), type (`text | number | select | boolean | price | discount | photos | location | contact`), required, options?, max?.

When populating `field_schema` from a `spec-detail-*.md` file (see "Frontend listing-form specs"), copy the conventions already used by the seeded categories (cars/phones/computers/electronics/home-and-land/jobs/services/fashion-and-beauty/furniture-and-decor/books-sports-and-hobbies/pets/foods) so entries stay consistent: reuse the module-level `conditionField` const in `categories.seed.ts` (do not redefine it); write photos inline as `{ key: 'photos', type: 'photos', max: 8 }`; map "Name / Phone Number (up to 3) / Email" to `contactName` / `contactPhones` (`max: 3`) / `contactEmail` (all `type: 'contact'`); fold "Address" + "(set on Google Maps)" into a `location` field plus a `text` `address` field (there is no separate maps field); key any "Type" picker as `type` with `type: 'select'` + `options`; labels are `en`-only. Use `type: 'number'` for a free numeric quantity and reserve `select` for enumerable numerics (`storage`, `year`). Home & Land's `size` is the one `number` key today, and **its unit lives on the display rather than in the input**: the post form renders a bare number with no suffix (what the captain's form mock shows), while the published specs grid appends `m²` via `VALUE_SUFFIX` in `ListingSpecs.tsx` — so the JSONB stores `"220"` and the detail page reads `220m²`. (This file has now been wrong in both directions on that detail: it first asserted the `m²` was in the form, then that no `m²` existed anywhere. Both surfaces are stated here as shipped.); reuse `conditionField` only when the form actually has a Condition field — not every category does (Home & Land forms carry no Condition/discount/free-delivery fields). The seed upsert in `src/db/seed.ts` writes `field_schema` on conflict, so re-running `db:seed` is idempotent. (Counting tip: `grep -c "fieldSchema:"` skips the `fieldSchema?:` type-def line.) When a spec-detail file states all subcategories of a main category share one form (Jobs/`spec-detail-six.md` and Services/`spec-detail-seven.md` both say "the same form"), apply one identical `fieldSchema` array to every subcategory. **The photos `max` is per-category — read each spec's own `Photo (0/N)` line; never generalize across categories:** Jobs (`spec-detail-six.md` = `Photo (0/1)`) → `max: 1`; Services (`spec-detail-seven.md` = `Photo (0/8)`) → `max: 8`; most categories use `max: 8`.

**`commonListingFields`:** the seed defines a module-level `commonListingFields` const — the 11-field set photos(max 8)/title(req)/price(req)/discount/description/location/address/deliveryFree/contactName/contactPhones(max 3)/contactEmail (the camera form minus any Type and Condition fields). Many subcategory forms equal this set exactly (e.g. all of Pets and Foods, and the no-Type Furniture blocks like `wardrobe-and-cabinets`). **By current convention these are written out INLINE**, field-for-field, matching the existing blocks — do **not** write `fieldSchema: commonListingFields`. No block references the const as a whole `fieldSchema` value; it is only ever spread for the photos field via `...commonListingFields.filter((f) => f.key === 'photos')`. (A spec-detail spec that recommends the bare const reference is wrong about the convention — verified this way in the Pets/Foods ships. Collapsing the inline duplication into a shared reference is a tracked follow-up; see Known gaps.)

**Seed (`src/db/seed.ts`):** runs geography → categories → brands → models → attributes → admin → reports → demo listings in order. All seeds are idempotent; the models + attributes seeds are insert-only (never overwrite admin edits). **`listings.seed.ts`** (2026-08-31) upserts 22 curated Khmer-market demo listings (spread across categories; real brand/type attribute names so feed filters match; USD prices; seeded provinces/districts; owner = the admin user; a few carry local `/sub-img` photo paths — those are bundled files, so by the DbImage rule they render as the card's empty state, not as photos — idempotent by title, and it DELETES the seven known test/junk titles ("car", "car 1-3", "car test 1", the Corolla test rows) so E2E debris never survives a seed. Note: listings creation now goes through the demo seed (plus the real post-form flow); demo rows are seed-owned (delete+reseed to change them, since the seed skips existing titles).

### Users schema

The `users` table relates to **six satellite tables**:

| Table                 | Purpose                                                                 |
| --------------------- | ----------------------------------------------------------------------- |
| `user_phones`         | Phone numbers (`phone unique`, `isPrimary`, owned by `userId`)          |
| `user_auth_providers` | One row per (user, provider): `telegram`, `phone`, `google`, `facebook` |
| `user_blocks`         | Directional blocks; unique `(blocker_id, blocked_id)`, both FKs cascade |
| `provinces`           | 25 Cambodian provinces (slug unique, seeded)                            |
| `districts`           | 208 districts; unique on `(province_id, slug)` (fully seeded)           |
| `communes`            | 1,652 communes; unique on `(district_id, slug)` (fully seeded)          |

Key columns on `users`:

- `username / primaryPhone / email` — unique via **partial unique indexes** (`WHERE deleted_at IS NULL`), so soft-deleted users release their identifiers for re-registration. Upserts targeting these columns must pass `targetWhere: isNull(users.deletedAt)` (see `mirrorSupabaseUser`), and single-row lookups must filter `isNull(users.deletedAt)`. Username generation lives in `src/users/username.util.ts` — `buildUsernameBase(first,last)` (lowercase/NFC, space-stripped) feeds `generateUniqueUsername(db,base)`: probes `users.username`, suffixes `base, base2, base3…` (skips 1), caps at 50 chars; the probe checks ALL rows including soft-deleted (stricter than the partial index). Wired into: Telegram login insert, `updateProfile` lazy backfill (only while `username === null`), and phone-OTP registration. Check-then-insert → a 23505 race is possible (see Known gaps).
- `provinceId / districtId / communeId` — nullable FKs to the geo lookup tables, **`ON DELETE RESTRICT`** since 2026-09-12 (a user's location must never be silently cleared by a geography re-seed)
- `deletedAt timestamp` — soft-delete; `status='deleted'` + `deletedAt=now()`
- `preferredLanguage default('en').notNull()` — also drives the admin UI locale (the `/wanderer/*` surface reads it via an `admin_locale` cookie seeded at login; the in-dashboard `LocaleSwitcher` writes back via `PATCH /users/me`). DTO allowlist: `en, km, zh, ko, id, vi`.

`user_phones` enforces at most one `isPrimary` row per user via a partial unique index (`user_phones_user_primary_uq`). `user_phones.phone` stays globally unique (not freed by soft-delete).

**Phone management endpoints** (all require JWT): `POST /api/v1/users/me/phones`, `DELETE /api/v1/users/me/phones/:phoneId`, `PATCH /api/v1/users/me/phones/:phoneId/primary`. Ownership is enforced via `and(eq(id), eq(userId))`.

**Block endpoints** (all require JWT): `GET/POST /api/v1/users/me/blocks`, `DELETE /api/v1/users/me/blocks/:userId`. Blocking is idempotent (`onConflictDoNothing`); a block in either direction makes chat sends fail with 403 (see Chat).

**Follow endpoints** (2026-09-28): `GET /api/v1/users/by-username/:username` (**`@Public()`** — returns the explicit `PublicProfile` allow-list: identity, `createdAt`, `isVerified`, both counts; never phone, email, role or moderation state), `GET/POST/DELETE /api/v1/users/:id/follow` (JWT — read status / follow / unfollow), `GET /api/v1/users/:id/followers` and `/:id/following` (JWT, offset-paginated via `ListFollowsDto`, every row carrying viewer-relative `isFollowing`), and `GET /api/v1/users/me/follow-counts` (JWT). Backed by **`user_follows`**, which mirrors `user_blocks` exactly — unique pair index + reverse index + `follower_id <> following_id` CHECK, both FKs `CASCADE` so `AccountPurgeService` keeps working (it hard-deletes `users` rows and depends on every inbound FK taking its rows along). **Follow and unfollow are both idempotent**: `POST` rides `onConflictDoNothing`, and `DELETE` deliberately does _not_ 404 on a missing edge (unlike `unblockUser`) because the control is a toggle whose end state is the whole contract — a double-tap must land on "not following", not an error. Following is refused with **403** when _either_ side has blocked the other (`isBlockedEitherWay`, reused from `chat/blocks.util.ts`), and a genuinely **new** edge writes one `follow.created` notification — the `returning()` row gates it, so a replay cannot double-notify. **The follower lists require a JWT on purpose:** that is what lets each row carry `isFollowing` without an N+1, and it is the one place this feature diverges from the rest of the read surface; the profile endpoint itself stays public. Nothing here is transactional with the notification — see Known gaps.

**Activity tracking:** `LastSeenInterceptor` (global `APP_INTERCEPTOR`) calls `ActivityService.touch(userId)` on every authenticated request. `touch` is fire-and-forget with a 5-minute in-memory throttle per user.

### Locations API

`LocationsModule` (`src/locations/`) exposes three public read-only endpoints:

```
GET /api/v1/locations/provinces
GET /api/v1/locations/provinces/:slug/districts
GET /api/v1/locations/provinces/:pSlug/districts/:dSlug/communes
```

All `@Public()`. The province list is `[]` when empty, but the two nested routes **throw 404** when the parent slug is unknown — unlike the feed endpoints' `[]` short-circuit. Rows are `{id, name, slug}` (plus the parent id from level 2). The post form's three-level Location cascade is driven off them (`getProvinces`/`getDistricts`/`getCommunes` in `lib/api/categories.ts`, exposed to the client as `getLocationDistricts`/`getLocationCommunes` in `actions/listings.ts`).

### Brands

`BrandsModule` (`src/brands/`) — lookup tables for brand/model selects on listing forms.

```
GET /api/v1/brands                        → all active brands, sorted by sort_order
GET /api/v1/brands?subcategory=<slug>     → brands linked to that subcategory ([] if slug unknown)
GET /api/v1/brands/:id/models             → active models for a brand ([] if none)
GET /api/v1/brands/:id/models?subcategory=<slug>  → only the models in that subcategory
```

**Models are scoped to subcategories (2026-09-22).** `models` is keyed by `(brand_id, slug)` alone, so it could not tell an iPad from an iPhone and `?subcategory=` did not exist — Tablets under Apple listed iPhones, and Xiaomi's phones showed under Cars For Sale. The dimension lives in a fourth table, **`model_subcategory_links`** (mirroring `brand_subcategory_links`, same shape and cascade), because a model may genuinely span two subcategories (Surface Pro is a tablet and a laptop).

**The filter rule:** with no `subcategory` param the brand's whole catalogue comes back (the admin Models page uses this). With one, the result is **models linked to that subcategory, plus models with no link at all** — an unclassified or admin-created model must never silently empty a picker, the same managed/global philosophy as `forSub`. A model linked only _elsewhere_ is excluded, which is the actual fix. Note the naive test (`subcategoryId != <this>`) would be wrong: it would drop a model linked to two subcategories from both, which is the case the link table exists for — `BrandsService.listModels` uses `inArray(linkedToThis) OR notInArray(linkedAnywhere)`.

All three routes are `@Public()`. Four DB tables: `brands`, `models`, `brand_subcategory_links` and `model_subcategory_links` (junctions). `MODEL_SEEDS` / `MOTO_MODEL_SEEDS` in `brands.seed.ts` are **grouped by subcategory** (`Record<brandSlug, Record<subcategorySlug, string[]>>`) — that grouping IS the classification, and `seedModels` seeds the links in a second pass, which is what makes it apply to the ~385 model rows that already existed (models are insert-only, so only the links are new). The motorcycle list stays flat and is wrapped at the call site, since every moto model is `motorcycles-for-sale`. **Model slugs spell `+` as `-plus`** (`slugify` in `seedModels`). A trailing `+` is meaningful — "Galaxy S25+" is a different phone from "Galaxy S25" — but `+` is outside the admin DTO's `SLUG_RE` charset. Until 2026-09-22 both slugified to `galaxy-s25`, and since the seed lists the `+` entry **first**, it won the slug and the **plain** Galaxy S21…S25 were silently dropped by `onConflictDoNothing` — the database was missing the base models, not the plus ones. Migration `0020_fix_plus_model_slugs` renamed the six rows that had already claimed a bare slug (`galaxy-s21`…`galaxy-s25`, `realme-12-pro`); it is a no-op on a fresh database. **`seedModels` now guards against the class of bug** via `findSlugCollisions` (`brands.seed.ts` — a pure exported function with unit tests in `brands.seed.spec.ts`): `onConflictDoNothing` discards a colliding model silently, so after the insert pass it compares each seeded name against the name stored at that `(brandId, slug)` and warns when they differ. Comparing **names** is what separates a real collision from an ordinary idempotent re-run, where every model "conflicts" because it is already there — a guard that warned on every conflict would be noise on every seed. The summary line counts collisions when there are any. Verified firing end-to-end 2026-09-22 by temporarily seeding a colliding name (`'iPhone 16*'`, which slugifies onto the existing `iphone-16`) — a method that needs no database mutation, so an interrupted run leaves nothing behind. **Nothing else in the codebase writes a model row** — `admin-models.service.ts:122` (admin `PATCH /admin/models/:id`) is the only writer; there are no triggers on `models`, no `pg_cron`, and the seed is insert-only. Assigning a model to a subcategory its brand is not linked to is **refused with a warning rather than written** — such a model could never be reached there; the seeded models left out for that reason are listed in a comment block above `MODEL_SEEDS` (ASUS's phones, Canon's camera bodies, Panasonic's Lumix, Philips's monitors, Vertu, Yealink…). **Surface Pro 10 is the live multi-link case** — it carries both `laptops` and `tablets`, which is the whole reason this is a junction table rather than a column on `models`. (Microsoft was linked to `tablets` on 2026-09-22 for exactly this; before that the guard refused the link.) The seed (`brands.seed.ts`) has two sets: `BRANDS` — 67 brands covering phones, tablets, smart-watches, and computers-and-accessories subcategories — plus `CAR_BRANDS` — 91 car brands (cars-and-vehicles → cars-for-sale), names/order taken from the web mock design (MG first), slug + icon derived from the app's local `/sub-img/car_vehicles/cars-for-sale/brands/*.png` design assets (interim icon source until these move to Supabase Storage; admins replace via the UI). `BrandSeed.icon?` lands only on INSERT — the brand `onConflictDoUpdate.set` never touches `icon`, so admin-uploaded icons survive re-seeds. A slug appearing in two sets is handled specially: the first occurrence upserts the row, later ones only wire `brand_subcategory_links` (+ null-icon backfill) so they can't clobber the earlier set's `sortOrder` (the one case: `xiaomi`, in both phones and cars; its car-grid position follows the phone order).

**`MOTO_BRANDS` (third set, 2026-08-31):** 31 motorcycle brands (`cars-and-vehicles → motorcycles-for-sale`), design order from the web mock (Honda first). Slugs derive from the asset filenames — the mock's `royal-enfeild`/`others` entries map to `royal-enfield.png`/`other.png`; names are mock-verbatim (including the "Royal Enfeild" spelling). Honda/Suzuki/BMW also appear in the cars set with a DIFFERENT logo asset: the moto entries take `-moto` slugs (`honda-moto`, `suzuki-moto`, `bmw-moto`) so each branch keeps its own row, icon, and design position (both grids render the same display name). The moto `other` row is the phones-family Other (sortOrder 999, admin-uploaded icon) shared across subcategories — the same shared-slug exception as `xiaomi`. Moto icons are the `/sub-img` assets (interim) until admins replace via the UI. `seedBrands` log counts all three sets.

`sort_order` is manually assigned — not auto-increment. `Other` always gets `sortOrder: 999` (phones set; the car set's `other-car-brand` is simply last in the design order). The `models` table is seeded with ~250 starter models (`MODEL_SEEDS` + `seedModels` in `brands.seed.ts`, insert-only) covering the major phone/laptop/printer/smartwatch brands plus car models for the design's model-bearing brands (mg/leapmotor/toyota — the mock's "Pirus" typo is seeded verbatim); admins add the rest via the admin Models page (each model carries an optional image; old images are cleaned up on update/delete via `removeByPublicUrl`). The brands list response shape is `{id, slug, name, icon, sortOrder}` — the field is `icon`, not `image` (models use `image`); brands do NOT nest models (`GET /brands/:id/models` is a separate call).

### Listings

`ListingsModule` (`src/listings/`) — marketplace listings with cursor-based public feed and offset-based owner feed.

**Feed filtering (`GET /api/v1/listings`):** `findFeed()` delegates slug resolution to a private `resolveQueryFilters(query)` helper. If any slug is not found, short-circuits with `{ data: [], meta: {...} }` — no error. The same pattern applies in `findMine()`.

Supported query params: `categorySlug`, `subcategorySlug`, `provinceSlug`, `districtSlug`, `q` (title ilike), `minPrice`, `maxPrice`, `condition`, `brand`, `bodyType`, and (since 2026-09-23) **`attrKey` + `attrValue`** — a generic pair filtering `attributes->>attrKey = attrValue` for every attribute grid whose key is none of the hardcoded ones. `attrKey` is validated to a plain identifier (`/^[a-zA-Z][a-zA-Z0-9]{0,39}$/`) and **bound as a parameter, never interpolated**, so it is a JSONB read rather than a path injection — locked by unit tests that compile the WHERE clause and assert the key arrives as `->>$n`. Half a pair applies nothing (matching the `districtSlug` rule below); `brand`/`bodyType` are untouched for existing callers. `districtSlug` without `provinceSlug` is silently ignored. **`brand`/`bodyType` match the display names stored in the `attributes` JSONB** (`attributes->>'brand'` / `->>'bodyType'`) — the same names the post form writes; slugs on the web are mapped slug → name at the page boundary.

**Ad creation** — `POST /api/v1/listings` (JWT): takes `categoryId`/`subcategoryId` as **UUIDs** (not slugs), inserts with `status='draft'`, `attributes` JSONB, `photos: [{url, path, sort}]` (max 8 — `url` = Supabase public URL, `path` = the `/files/sign` storage path; no upload tokens). `POST /api/v1/listings/:id/publish` (owner) flips to `status='active'` + `expiresAt = +30d`; the feed only shows `active` — a client post flow must call create **then** publish. Update/PATCH swaps `listing_photos` rows and best-effort cleans up dropped photos after commit.

**Cursor pagination** (feed): cursor encodes `{ createdAt, id }` as base64 JSON. Invalid cursors are ignored.

**Owner listing** (`GET /api/v1/listings/me/all`): offset pagination, adds `status` filter.

### Likes & Saved (`src/reactions/`, 2026-10-05)

`ReactionsModule` (`src/reactions/`) owns the two edge tables behind every heart and bookmark: **`listing_likes` + `listing_saves`** (`db/schema/reactions.schema.ts`, migration `0028_acoustic_chat`) — mirroring `user_follows` (unique pair index, reverse `listing_id` index, both FKs CASCADE so `AccountPurgeService` keeps working). No self-check: liking your own listing is allowed.

```
POST|DELETE /api/v1/listings/:listingId/like   → { liked, likeCount }
POST|DELETE /api/v1/listings/:listingId/save   → { saved }
GET  /api/v1/users/me/likes|saves              → paginated listing rows (the feed's shape)
GET  /api/v1/users/me/reactions                → { liked: uuid[], saved: uuid[] }
```

Toggles are **idempotent both ways**: `POST` rides `onConflictDoNothing`, and `DELETE` never 404s at all (the toggle's end state is the whole contract, same as unfollow — a stale unlike of a hard-deleted listing returns `{liked:false}`). The only 404 is a missing listing row **on the POST side** — mirroring `findById`, which serves **any status**, so a control that renders on the detail page is never present-but-refused. The list reads filter `status != 'deleted'` (a removed ad leaves "my likes"; the edge survives a restore); the id-set read is unfiltered (it only lights up rendered cards). `likeCount` is computed per read (no counter column) and rides the listing detail response and every like-toggle response, so the detail's "N Likes" never refetches; `ListingsModule` imports `ReactionsModule` (no cycle).

**Web side:** the `(user)` layout reads both id sets once per signed-in render (fail-soft to empty) and wraps the tree in `components/reactions/reactions-provider.tsx`; `useReactions()` is the single source for every control (grid + list hearts, the ⋮ Save/Unsave — the menu stays open — the detail row's Save, and the detail's "N Likes" + count). Toggles are optimistic with rollback-toast, disable while pending (per listing, either kind), bounce visitors to `/login` with a "Sign in to like/save" toast, and ignore non-UUID (mock) ids entirely — a demo heart is inert, never a request or an error toast. A row toggled off mid-session drops out of the `/me` lists live (`isToggledOff`, not membership — the seed sets fail soft). `/me/likes` + `/me/saved` render the real listings via `components/profile/reaction-ads-panel.tsx` (loading/error/empty distinct — an empty list and a failed one must not look the same — plus "Load more"; the existing "No Result!" empty designs are kept). Not included: notifications on like/save; admin surfaces; counts anywhere but the detail control.

### Chat

`ChatModule` (`src/chat/`) — 1:1 buyer↔seller messaging. **REST is authoritative; a WebSocket gateway is an optional low-latency push on top, not a replacement.** Every message — REST or WS — goes through the single `ChatService.sendMessage` write path, so validation exists once. Its three pre-write checks (recipient existence, block check, listing ownership) run concurrently via `Promise.all` rather than sequentially — each is an independent read, and each DB round trip is real latency against the remote Supabase pooler, so this is the difference between one queueing round trip and three under concurrent send load. See `DATABASE_POOL_MAX` above: the shared postgres.js pool (default 20, not chat-specific) is the actual scaling limit under concurrent chat traffic, not `ConnectionRegistry` (verified empirically — 20 concurrent WS sends across 2 connections showed 0 drops/duplicates/misrouting; latency scaled with pool contention instead). **Per-contact threads**: exactly one `conversations` row per unordered user pair (CHECK `user_a_id < user_b_id` + unique; the service canonicalizes the pair and upserts with `onConflictDoUpdate`, bumping `last_message_at`). A message may carry an optional `listingId` context card (FK `ON DELETE SET NULL`). All routes require JWT. Full design + diagrams: `src/chat/README.md`.

```
POST /api/v1/chats/messages          → send { recipientId, body, listingId?, e2eHeader? | e2e?, attachmentIds? } — E2E required; find-or-creates the conversation
GET  /api/v1/chats                   → inbox: cursor on (lastMessageAt, id); items carry otherUser, lastMessage, unreadCount
GET  /api/v1/chats/unread-count      → { total } for the badge
GET  /api/v1/chats/with/:userId      → resolve thread with a user (read-only — never creates; conversation may be null)
GET  /api/v1/chats/:id/messages      → history (cursor=, DESC) or polling deltas (after=, ASC); meta adds latestCursor + peerLastReadAt
POST /api/v1/chats/:id/read          → bulk mark-read; returns { marked }
```

Send rejections: self (400), missing E2E envelope (400 `Encrypted messages are required`), empty body (400), any `imagePath` (400 `Unencrypted chat images are not accepted` — the legacy public imagePath is rejected for new sends), recipient missing/soft-deleted (404), block in either direction (403 `Messaging unavailable`), listing owned by neither participant (400). Non-participants get 404 (not 403) on conversation routes — no existence oracle. Clients poll with `after = meta.latestCursor`; read receipts surface via `peerLastReadAt` (= `max(readAt)` of my messages, valid because mark-read is bulk).

`messages.created_at` and `conversations.last_message_at` are `timestamp(3)` — cursor values roundtrip through JS Dates (ms precision), so µs columns would re-deliver the boundary row on `after` polls.

**WebSocket gateway** (`chat.gateway.ts`, `/ws/chat`): authenticates via `?token=` query param, `Authorization` header, or the `user_access_token` cookie (browser WS can't set headers), verifying signature+expiry via `JwtService.verify` and then running the same soft-delete DB check `JwtStrategy.validate` does on the REST path (parity — a soft-deleted user can no longer keep a working socket until access-token expiry). `send_message` is rate-limited in-memory, 30/min per user, mirroring the REST route's `@Throttle`; its payload is validated in the handler with the REST `ValidationPipe` options (the envelope is an interface, so the global pipe can't see it), and every send is answered with exactly one frame echoing `clientMessageId` — `ack` `{conversationId, message}` or `error` `{code, message, details?}` with the same codes as the REST error envelope (errors are caught in the handler because `GlobalExceptionFilter` is HTTP-only). `markRead` pushes a `read` `{conversationId}` event to the other participant so a WS-connected sender's receipts update live (their delta poll is paused while the socket is up). `ConnectionRegistry` is still an in-memory per-process `userId -> sockets` map — a given instance can only write to its own local sockets — but `ChatPubSubService` (`chat-pubsub.service.ts`) now publishes every push (`message`, `inbox_update`, `unread_count`) over Redis pub/sub (reusing the BullMQ Redis connection), so every instance's gateway subscribes and delivers to its own locally-connected recipient. Real-time push therefore reaches a recipient on _any_ backend instance, not just the sender's; an offline recipient still gets the message via their next `after=` poll, so correctness never depends on the socket. `HeartbeatService` pings every open socket every 30s and evicts any that hasn't ponged in 40s. On the web client, `use-chat-ws.ts` holds one shared WebSocket per tab (ref-counted across the nav unread badge, inbox list, and any open thread) and `inbox_update`/`unread_count` pushes replace the flat-interval inbox/badge poll whenever that socket is connected — see `CHAT_POLL` in `use-chat-polling.ts` for the fallback tiers used the rest of the time.

**End-to-end encryption** (X3DH + Double Ratchet over `@noble/curves`, Signal-protocol shaped): `SendMessageDto.e2eHeader` (validated by `E2eHeaderDto`) marks a message as E2E — `body` becomes base64 ciphertext (max 24000 chars vs. plaintext), mutually exclusive with `e2e`; the legacy `imagePath` is rejected outright, and media (images, voice notes) travels as encrypted v2 attachments. The header carries the Double Ratchet fields (`dh`, `pn`, `n`) plus, only on a session's first message, the X3DH initial-message fields (`identityKey`, `ephemeralKey`, `oneTimePrekeyId`, `signedPrekeyId`). Stored verbatim in `messages.e2eHeader` (JSONB) alongside `messages.isE2e`. Key material lives in two tables: `user_e2e_identities` (one row per user — X25519 `identityKey` for DH, a **separate** Ed25519 `identitySigningKey` for signing `signedPrekeyPublic`, since `@noble/curves` doesn't expose the Edwards↔Montgomery conversion Signal's XEdDSA uses to make one key do both) and `user_e2e_one_time_prekeys` (claimed one at a time via a partial index on unused rows). `E2eKeysController` (`/api/v1/chats/e2e/keys`): `POST` registers/rotates a user's keys + replenishes one-time prekeys, `GET me/prekey-count` reports remaining stock, `GET :userId/bundle` fetches a peer's bundle (identity key, signing key, signed prekey + signature, one claimed one-time prekey) to start an X3DH session. The backend only stores and relays key material and ciphertext — it never sees plaintext or private keys. **v2 multi-device** (`e2eVersion=2`): one identity per browser (`user_e2e_devices`), the message key wrapped per recipient/sender device in `message_envelopes`; a stale device list → 409 `E2E_DEVICES_MISMATCH` with `details` for the client to fix and retry. **History backup** (`e2e-backup.*`, `/chats/e2e/backup`): a per-account backup key (BK) encrypts plaintext segments; a new device gets BK only via the account passcode (argon2id → server-rate-limited unlock); device approval was removed on 2026-10-26, and `0041_brainy_plazm` drops `chat.e2e_history_requests`. Plan + status: `tasks/plan-e2e-multi-device.md`; open security items: `src/chat/README.md`. **Encrypted attachments** (`chat-attachments.*`, `/chats/attachments`, design `docs/e2e-attachments.md`): the browser resizes images to WebP, encrypts each file with its own AES-256-GCM key (frozen `E2E_FILE_V1` format: `NPF`+version, IV, ciphertext+tag) and uploads ciphertext to the **private** `chat-files` bucket (octet-stream only, 25 MB cap); keys, MIME types and thumbnails ride inside the v2 E2E message. `chat.attachments` tracks `pending → uploaded → attached`; `complete` trusts only the size read from storage; `POST /chats/messages` attaches `attachmentIds` in the send transaction with one conditional `UPDATE`; downloads use 5-min signed URLs issued only to participants; integrity is recipient-verified (hash + GCM tag), so there's no server-side hash. An hourly BullMQ job (`chat-maintenance` queue) deletes objects + rows never attached within 24 h. Legacy `imageUrl`/`imagePath` rows stay in the public bucket and still render; `NEXT_PUBLIC_E2E_ATTACHMENTS=off` is now a kill switch that disables encrypted media (images, voice notes) entirely — there is no plaintext fallback, so media fails closed.

### Files

`FilesModule` (`src/files/`) handles file uploads to Supabase Storage. Signed upload URLs are generated server-side; the client uploads directly to Supabase. Public URLs are returned for confirmed uploads. Bucket name is configured via `SUPABASE_STORAGE_BUCKET` (default: `listings`).

**Upload scopes** (`POST /files/sign`, `SignUploadDto.scope`): `avatar | cover | listing | chat | category | subcategory | brand | model | attribute` — `chat` paths are per-user (`chat/{userId}/…`); the scope is now legacy — the web no longer signs chat uploads, since new sends reject `imagePath`. `DELETE /files` takes `{ paths: string[] }` for path-based deletion.

**Image cleanup on replace/delete:** `FilesService.removeByPublicUrl(publicUrl)` (`files.service.ts:105-125`) derives the storage path from a public URL, silently skips non-storage values (`/placeholder.svg`, foreign URLs), and warns-but-never-throws. The established pattern: read the prior `image`/`icon` inside the DB op, call `removeByPublicUrl(old)` **after commit**, gated on the value actually changing. Currently wired for: attributes, brands, models, categories/subcategories (icons), user avatar, user cover, and listing photos (removed-from-payload diff). **Not** wired for: admin user soft-delete (avatar/cover stay live in storage), chat images (no message-delete endpoint exists by design), and listing soft-delete (restore must work).

### Payments

`PaymentModule` (`src/payment/`) — gateway-agnostic payment processing feeding a double-entry ledger; the full design (table layout, entity map, outbox/queue placement, lifecycle sequence, current status) lives in [`src/payment/README.md`](apps/backend/src/payment/README.md), the canonical Module README example. One thing that README won't flag because it's a backend-wide convention question, not a module detail: **this module's use-cases are written in [Effect](https://effect.website) (`effect` npm package), not plain async/await NestJS services.** `use-cases/**/*.use-case.ts` (split into `use-cases/payments/` — payment_transaction/payment_attempt/provider-event lifecycle — and `use-cases/ledgers/` — double-entry posting, mirroring the processing/ledger table split; the top-level `use-cases/index.ts` re-exports both so every consumer still imports from one place) are `Effect.fn`-wrapped generators that `yield*` a `DbClientTag` (`src/db/db.provider.ts` — an Effect `Context.Service` wrapping the same Drizzle client the `DRIZZLE` token provides everywhere else) and fail with `Schema.TaggedError` subclasses (`use-cases/payments/errors.ts` / `use-cases/ledgers/errors.ts`) instead of throwing. `PaymentsController` is the only bridge back to NestJS: its private `run()` helper provides `DbClientTag.layer(this.db)`, runs the effect with `Effect.runPromiseExit`, and maps a typed failure to an `HttpException` via a `switch` on `error._tag`; an unmodeled defect falls through to `GlobalExceptionFilter` as a 500. This pattern is currently unique to `payment/` — don't reach for `effect` in other modules without a deliberate decision to extend the convention.

### Adding a new feature module

1. Create `src/<feature>/{feature}.module.ts`, `.service.ts`, `.controller.ts`.
2. Add DTOs to `src/<feature>/dto/`.
3. Import the module in `AppModule`.
4. Mark public endpoints with `@Public()`. Everything else requires a valid JWT automatically.
5. Do **not** import `DbModule` or `SupabaseModule`; their providers are available globally.

**For admin-only features**, add the controller + service to `AdminModule` instead of creating a separate module. Register them in `src/admin/admin.module.ts`. The controller uses `@Roles('admin', 'super_admin')` (guard is inherited from `AdminModule` or applied at the controller level if the feature has its own module).

**Exception:** the attributes feature owns its own module at `src/attributes/` (`AttributesModule` — admin-scoped routes at `/admin/attributes/:type`, registered in `AppModule`, imports `FilesModule`). It was decoupled from `AdminModule` so it can grow a public surface; keep admin-only features in `AdminModule` unless they have the same trajectory.

## Web app architecture (marketplace + admin dashboard)

The `apps/web` Next.js 16 app is the admin dashboard. It runs on port **3001** and talks to the backend at `http://localhost:3000/api/v1` (configurable via `API_URL` env, default baked into `lib/api/client.ts`).

### Auth flow

Admin and user auth are **split onto separate surfaces**:

**Admin (`/wanderer/*` — non-localized, no `/[locale]` prefix):**

1. `actions/admin-login.ts` (server action) calls `POST /api/v1/auth/login`, rejects unless `user.role` is `'admin'` or `'super_admin'`, then calls `setAdminSession()` to persist `accessToken` + `refreshToken` in **httpOnly cookies** (`admin_access_token` / `admin_refresh_token`). Also seeds the `admin_locale` cookie from `user.preferredLanguage`.
2. `proxy.ts` (Next.js 16 replacement for `middleware.ts`) guards `/wanderer/dashboard/**` — if no `admin_access_token` cookie, redirects to `/wanderer/login` (with `?next=`). **Cookie presence is the proxy's only check**, so it is not the real gate: `app/wanderer/dashboard/layout.tsx:19-25` calls `getCurrentUser()` and `redirect("/wanderer/login")` unless the session resolves to an `admin`/`super_admin` — "defense in depth" against a non-admin or stale token rendering the shell. A placeholder cookie therefore passes the proxy and is still bounced by the layout (verified 2026-09-15); a real admin session is required to see any dashboard page. The entire `/wanderer/*` surface bypasses next-intl entirely (never gets a locale prefix). Stray locale-prefixed wanderer URLs (e.g. `/en/wanderer/login`) are redirected to strip the locale.
3. `app/wanderer/layout.tsx` is a **second root `<html>` layout** (Next.js supports multiple root layouts when no `app/layout.tsx` exists). It reads the `admin_locale` cookie, validates it against `routing.locales`, and wraps children in `NextIntlClientProvider` with the cookie-sourced locale + directly-imported `messages/${locale}.json`. This bypasses `i18n/request.ts` (which is URL-segment based) entirely.
4. The in-dashboard `LocaleSwitcher` (`components/dashboard/locale-switcher.tsx`) calls `actions/admin-locale.ts`, which sets the `admin_locale` cookie + `PATCH /users/me { preferredLanguage }`, then `router.refresh()` re-renders the layout in the new locale.
5. `actions/logout.ts` (`adminLogout`) clears session + locale cookies and redirects to `/wanderer/login`.

**User (`/[locale]/login` — locale-prefixed):**

1. `actions/login.ts` (server action) calls `POST /api/v1/auth/login` and accepts any authenticated user (no role gate). **Phone-shaped identifiers** (`^0\d{7,9}$` — local-only; typed `+855…` or `855…` is treated as a username and fails) route instead to `requestLoginOtp` (`actions/otp.ts` → `POST /auth/otp/login`), which validates the password first, then sends the OTP and redirects to `/{locale}/otp?phone=<E.164>`.
2. **Distinct cookies:** admin and user sessions use separate httpOnly cookie pairs — `admin_access_token` / `admin_refresh_token` (admin) vs `user_access_token` / `user_refresh_token` (user). A user login cannot satisfy the proxy's admin-cookie guard, and `serverFetch` reads admin cookies only.
3. **Post-login destination is `/me`.** Both the login form (password mode) and the OTP verify success handler push `/me` — after any successful user login/register the user lands on their account page first, never the home feed.

`serverFetch<T>(path, init?)` in `lib/api/client.ts` reads the **admin** httpOnly cookie (`admin_access_token`), injects `Authorization: Bearer`, unwraps the `{success, data, meta}` envelope, and **transparently refreshes** on 401 (calls `POST /auth/refresh`, sets new cookies, retries once). On refresh failure, clears session. Throws `ApiError` on non-ok responses. **`userServerFetch<T>(path, init?)` is the user-side twin** — identical behavior but reads USER cookies (`getUserAccessToken`/`getUserRefreshToken`) and clears the user session on refresh failure; same cookie-write-during-RSC-render caveat applies. `getCurrentUser(): SessionUser | null` (`lib/auth/current-user.ts`, server-only) is the fail-soft session reader used by the `(user)` layout — anonymous fast-path (`no access or refresh token`) returns `null` with zero backend calls; any error degrades to visitor chrome. `actions/logout.ts` exposes both `adminLogout()` and `userLogout()`.

`clearAdminSession()` on 401 failure in `serverFetch` — cookie writes throw during RSC render (read-only context), which is caught and swallowed (token persists until next mutation).

### Category + subcategory pages (backend-driven)

`/[locale]/category/[categorySlug]` and `/[locale]/category/[categorySlug]/[subcategorySlug]` are **async RSC** fetching `GET /api/v1/categories/:slug` (one call each — the response nests subcategories, so the subcategory page `.find()`s by slug; both pages pass the locale via `Accept-Language` and render backend names directly). The data plumbing lives in `lib/api/categories.ts` (server-only — `CategoryGrid`-style raw `fetch`, `cache: "no-store"`, envelope unwrap, `null`/`[]` on failure):

- `getBrandsForSubcategory(subSlug)` → `BackendBrand {id, slug, name, icon}` (map `icon` → OptionGrid's `image` at the page boundary)

## Schema domains beyond the core

### Subscriptions (`subscriptions.schema.ts`)

The admin UI manages a three-level catalog (`subscription_categories → subscription_packages → subscription_terms`), but a subscription category is a **group** in the API and entitlement model. Each group sells at most one package per fixed tier (`bronze|silver|gold`), and each package carries fixed 3/6/12-month terms. `subscription_category_subcategories` assigns each listing subcategory to at most one group; a held subscription grants the package limits across that group's scope, while unheld/out-of-scope ads use the configured free plan.

- `subscription_packages` is unique on `(categoryId, tier)`; parent group deletion cascades through packages and terms.
- `subscription_packages` feature fields are **integers** (`photos`, `ads`, `renews`, `autoRenews`, `videos`). `autoRenews` and `videos` are stored but are not enforced by current listing features, and are no longer shown on customer pricing/checkout.
- `subscription_terms` holds `durationValue` + `durationUnit`, numeric `price`, and `discount`/`discountType`. Admin writes are fixed to 3/6/12 months (`duration_unit = 'month'`; 12 displays as "1 Year"); terms outside that set are retired (`is_active = false`), not deleted.
- The free plan is admin configuration: singleton `free_plan_settings` plus `free_plan_ad_limits` caps for one listing category or subcategory. Public `GET /subscriptions/free-plan` exposes the current sheet.
- `user_subscriptions` stores a purchase-time `priceUsd`, `subscription_category_id` group, `expiresAt`, `superseded_at`, and typed `superseded_reason` (`upgrade|replaced|expired|revoked`). A partial unique index enforces one current row per `(user_id, non-null group)`; different groups can coexist. Status is **derived** from expiry/supersede fields, not stored.
- Admin `POST /admin/user-subscriptions/:id/revoke` conditionally marks a current row `revoked`, keeps history, and reconciles the user's listings. Group-scope and free-plan edits enqueue a BullMQ reconciliation (a burst collapses into one waiting job; an edit during a running sweep queues one more behind it); the recurring 10-minute sweep is the backstop. There is no outbox handoff for this recomputable work.
- Deleting a group nulls existing subscriptions' group FK and cascades its catalog. Entitlement loading ignores null-group rows, so group deletion can remove a holder's allowance; confirm/migrate or revoke those subscriptions before deleting a live group. See [`apps/backend/src/admin/subscriptions/README.md`](apps/backend/src/admin/subscriptions/README.md) for lifecycle and remaining gaps.

### Reports (`reports.schema.ts`)

- `report_reasons`: admin-managed picklist, unique on `(targetType, reason)`, discriminated by `targetType` (`user`|`listing`).
- `user_reports`: `reporterId` → `targetUserId`, optional `reasonId` (set null on delete), `imagePaths` JSONB string array, `status` (`pending|approved|rejected`), `reviewedById`.
- `listing_reports`: `reporterId` → `listingId`, same status/reviewedBy pattern.

Admin list endpoints batch-lookup user names (reporter + target) via `inArray` to avoid Drizzle's double-JOIN alias limitation.

### Attributes (`attributes.schema.ts`)

Single generic `attribute_options` table with a free-form `type` discriminator (`varchar(60)`, **not validated** — a typo'd type in the API silently creates a new set). Unique on `(type, slug)`. Optional `categoryId` FK + `subcategoryIds` JSONB (denormalized mirror of admin UI selections — **UUIDs, not slugs**, so client-side filtering must compare against the subcategory `id`).

**The scoping rule (`forSub` in `apps/web/actions/listings.ts`) — this is what makes unticking authoritative.** A set where _any_ row carries `subcategoryIds` is **managed**, and the ticks are the whole truth: a subcategory not ticked for a row does not see it. A set where _no_ row is linked anywhere is a **global picklist** and returns in full, so scoping can never silently empty a field. The rule is decided on the **set**, not on this subcategory's slice — the earlier "if nothing is ticked _for this subcategory_, return everything" had a nasty edge: unticking the last row of a managed set **resurrected the entire list**, so the field grew exactly when it should have emptied. Two consequences worth knowing: (1) the moment a row of a global set is ticked anywhere, that set flips to managed for _every_ subcategory at once; (2) a managed set that a subcategory simply has no ticks for renders **empty**, which is correct — `vehicles-for-rent` and `cars-for-sale` had no colour tick for a long time and only worked by the fallback. Admin CRUD at `/admin/attributes/:type`, served by the standalone `AttributesModule` (`src/attributes/`, `@Roles('admin', 'super_admin')`). The module also exposes **public reads** (`PublicAttributesController`, `@Public()`): `GET /api/v1/attributes/:type` (one set; admin pages + ad-hoc use) and `GET /api/v1/attributes?subcategoryId=<uuid>` (`listBySubcategory`, JSONB `@>` containment — ONE call returning every row linked to a subcategory; the web subcategory pages use this instead of per-type fetches). Note `AttributesService.list(type)` returns the full row (`id/type/slug/name/image/categoryId/subcategoryIds/sortOrder/isActive/…`) with **no `isActive` filter**, ordered by `sortOrder`.

**Data is seeded** (`src/attributes/seeds/attributes.seed.ts`, **insert-only** `onConflictDoNothing` — admin edits survive re-seeds). 19 types seeded (~279 rows): `colors, rams, cpus, storage_phone, storage_computer, screensize_laptop, screensize_monitor, bodytypes, enginetypes, vehicletypes, accessories, jobtypes, networks, bedrooms, bathrooms, facings, experiences, vgas, types`. The `types` picklist spans computer parts / cameras / TVs-audio / property / fashion / furniture / musical instruments; rows sharing `(type, slug)` (e.g. the many "Other - ផ្សេងៗ" rows) are merged by the seed's dedupe pre-pass, unioning `subcategories`. Seed slugs must match the DTO `SLUG_RE` (dev-time assertion throws otherwise).

**Images are never seeded** — every row starts `image: null`; admins upload via the admin UI (`ImageUpload` scope `attribute` → Supabase → public URL stored in `image`). Only 5 types are image-bearing (`hasImage: true`): `bodytypes, accessories, jobtypes, types, networks`. The single exception: after the insert loop the seed **gap-fills car body-type icons** (null-only UPDATE for the 9 car slugs → the web app's local `/sub-img/car_vehicles/cars-for-sale/body_type/*.png` assets; the `other-type` row maps to `other.png`) — non-null images are never touched. Since 2026-08-31 `BODY_TYPES` carries the full 21-row set (cars + lorries + the 5 vehicles-for-rent types motorcycle/bicycle/tuk-tuk-and-remork/city-bus/express-bus) in the **rent design order** (Motorcycle, Bicycle, Tuk Tuk, cars, buses, trucks, Other; convertible stays cars-only at its slot): one global `sortOrder` sequence keeps every subcategory's _filtered_ grid in its own design order, so re-seeds (insert-only) leave existing rows' links/order alone and the rent links + order on already-seeded DBs were applied as a one-time dev-DB SQL (the seed covers fresh DBs). The rental-type icons gap-fill from `/sub-img/car_vehicles/vehicles-for-rent/body_type/*.png`.

**`years` is generated, not stored.** `AttributesService.list('years')` computes `currentYear+1 → 1980` descending at read time (`categoryId` = cars-and-vehicles, `subcategoryIds` = cars-for-sale/motorcycles-for-sale, falling back to null/[]); `create`/`update`/`remove` reject `type === 'years'` with a 400.

**A type the web page doesn't know is invisible on the storefront:** the subcategory page renders only sets whose `type` appears in its `ATTRIBUTE_SET_TITLES` map (19 entries), so a newly seeded/admin-created type needs an entry there before it can appear as a grid. The DB currently carries three types outside both that map and the seed list — `condition`, `taxtypes`, `transmission` (2 rows each, all with empty `subcategoryIds`) — leftovers that render nowhere.

**Admin UI is trimmed to 6 types** — `lib/attribute-types.ts` (`ATTRIBUTE_TYPES`, the source of truth): bodytypes, accessories, jobtypes, types, networks, years (years is `readOnly: true`). Of the 19 seeded types, those 5 are manageable and the other **14** stay readable via the API but have no admin page/sidebar entry (spec-fixed plain dropdowns needing no management). `years` is the one managed type that is **generated, not seeded** — which is why the counts differ.

**`vehicletypes` is retired (2026-09-16, captain's call).** It and `bodytypes` held the **same 21 vehicle kinds** — every slug identical bar `other-type`/`other` — as two separate literals in `attributes.seed.ts`, neither derived from the other. Only `bodytypes` is admin-managed, so ticking a Body Type had **no effect** on the rent form, which read the duplicate instead; the rent browse page also rendered _both_ grids with 5 values appearing twice. `getVehicleTypes()` is deleted, Vehicles For Rent's **Vehicle Type** block now reads `config.vehicleKinds` (the same resolved list the `bodyType` block uses), and `vehicletypes` was removed from the browse page's `ATTRIBUTE_SET_TITLES`. **The 21 `vehicletypes` rows are still in the DB, unread** — deleting them is a separate decision. Ticking a Body Type row now controls both the rent form and the rent grid; each set is scoped by its `subcategoryIds`, so a value must be ticked for every subcategory that should offer it. **The sidebar is NOT derived from `ATTRIBUTE_TYPES`** — `components/dashboard/app-sidebar.tsx` hardcodes its own list, so a new type needs an entry in both; the hub (`dashboard/attributes/page.tsx`) _is_ derived and picks it up automatically. The dynamic route `dashboard/attributes/[type]/page.tsx` validates the slug against `ATTRIBUTE_TYPES` (404 otherwise) and renders `<AttributeManager type title hasImage? readOnly? />` (`components/dashboard/attribute-manager.tsx`). `readOnly` hides the Add button + per-row actions. Client-side search matches name/slug/category/subcategory names and resets to page 1.
