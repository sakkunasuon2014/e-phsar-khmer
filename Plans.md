### Plan: Bakong demand-driven polling — poll only while a payment is open (2026-10-31)

**Purpose**: Bakong has no webhook or push, so something must ask. Make that asking happen only while a payment is open (armed by issue, idle when none), with one poller and batched calls, instead of a BullMQ chain plus a 15 s reconciler that both ask per attempt. Settlement durability is out of scope: the owner tested that a paid QR settles after a page refresh.

**Spec delta**: no root `spec.md`. Record in `payment/providers/bakong/README.md` and `ARCHITECTURE.md`: "Polling is demand-driven: armed when a payment is issued (first `payment.attempt.poll_requested`), idle with zero open attempts. Settlement is server-driven and independent of any client; the UI only reads state."
**team_validation_mode**: `manual-pass` (no sub-agents).
**Not observed**: whether `check_transaction_by_md5_list` exists in NBC's official docs (only third-party SDKs mention it, max 50 per call); whether Bakong rejects payment of an expired dynamic KHQR; whether `DATABASE_URL` is a pooler (secret, not read). `not_observed != absent`.
**Rejected**: Postgres LISTEN/NOTIFY. It needs a long-lived session connection (impossible on serverless), NOTIFY is lossy so a table sweep is still required, and Bakong never notifies us. The outbox plus `wakeupAfterCommit()` is already the in-process event. Revisit only with an always-on worker on a direct connection.
**Known gap on serverless**: no live instance means no poller. A paid QR waits until a request boots one. Task 2.1 decides the wake-up.

### Plan: Backend background-work audit — stop the Vercel resource burn (2026-10-24)

**Purpose**: the backend runs as a container on Vercel (`Dockerfile.vercel`) and never idles, because several in-process loops run for as long as the container lives. Cut idle and per-payment background work without losing payments or retries.

**Spec skip reason**: there is no root `spec.md`. Phases 0–2 are infra and config tuning with no change to product behaviour. Phase 3 changes how fast a paid KHQR is detected, so once the option is chosen, record it in `payment/providers/bakong/README.md` and `ARCHITECTURE.md`.
**team_validation_mode**: `manual-pass` (no sub-agents were used; Product, Architecture, Security, QA and Skeptic were each considered by hand).
**Open fact, `not_observed`**: which Vercel limit was hit (Active CPU, memory, invocations or build minutes), and on which project (backend or web). Only the backend has background loops. Phase 0 confirms it.

### Plan: Keep E2E, stop the "Sent before this device was set up" wall (2026-10-26)

**Purpose**: a second browser, a cleared profile or a new phone shows a run of "Sent before this device was set up. Restore your history with the backup passcode." Keep end-to-end encryption exactly as strong, but make a new device read as much history as the account can possibly give it, and say something useful about the rest.

**Spec delta** (`docs/e2e-encryption.md`, new section "History availability"; there is no root `spec.md`): a message is readable on a device iff (a) the message carries an envelope for that device, or (b) some device of the account **decrypted it while holding the backup key (BK) and uploaded it**. Today (b) is true only for messages a device happened to _display_. This plan makes it true for every message a signed-in device _received_. Private keys, ratchet sessions and BK never reach the server in the clear (unchanged). The "Encrypted backup / key recovery" non-goal in that file is out of date and is rewritten.
**team_validation_mode**: `manual-pass` (no sub-agents; Product, Architecture, Security, QA and Skeptic considered by hand).
**Lint/formatter baseline**: present (eslint, prettier, `tsc`, `pnpm --filter web test` = `node:test` over `lib/**/*.test.ts`, backend jest). No setup task.
**Reuse check**: `lib/e2e/stub-engine.ts` already exists for tests; `startVisiblePoller`, `useNotificationEvents`, `fetchInbox`, `fetchMessages` and `decryptMessage` are reused as they are. Nothing new on the crypto side.
**Not observed**: how many of the unrecoverable messages in the dev DB were never displayed on any device (segments are ciphertext under BK, so this cannot be counted from the server).

### Plan: Signal-model key availability — a chat partner is never "not set up yet" (2026-10-26)

**Purpose**: replace "This person hasn't set up encrypted messaging yet. Ask them to open Messages once." with the Signal/WhatsApp invariant: **an account that has signed in always has a published prekey bundle, and a sender can always encrypt to it, whether or not the recipient is online.** Keep E2E strictly (decision #6: no plaintext fallback, ever). Chosen with the owner on 2026-10-26 after comparing Signal/WhatsApp, Telegram (server-readable default chats, opt-in Secret Chats that need the other side to accept) and Messenger (staged upgrade; fallback for non-upgraded partners is not documented by Meta). Supersedes the "e2eNoKeys" copy; complements the "Keep E2E, stop the wall" plan above (that plan fixes reading history on a NEW device, this one fixes SENDING to a partner).

**Spec delta** (`docs/e2e-encryption.md`, new section "Key availability"; there is no root `spec.md`): (1) _Registration invariant_: every signed-in browser registers a device before it does anything else, triggered by the auth flow itself, not by which page renders. (2) _Targetability invariant_: a user with at least one non-revoked device is always targetable; staleness may shrink the set but never empties it. (3) _No-device case_ (an account that never signed in on an E2E build): the sender HOLDS the message locally, nudges the recipient with a content-free notification, and sends automatically once a device exists. Nothing is ever sent in the clear and the server never holds a message body it could read.

**Risks and residual limits (stated, not hidden)**:

1. **A message to a stale device is readable only if the seller returns on that same browser.** If they return on another browser or after clearing data, that browser is a new device with no envelope for it, and only the history backup can help (the "Keep E2E, stop the wall" plan). K2.1 trades silent refusal for this limit, which is what Signal-style systems accept. The sender's UI should not promise delivery on read (no change planned).
2. **Held plaintext sits in the buyer's IndexedDB** until sent or expired, the same exposure as the decrypted-message cache that already exists there.
3. **The nudge reveals that someone wants to talk**, never what they said. Rate limit and block check are in the DoD.
4. **K2.1 changes the envelope set the server validates.** Every place that computes the set must go through the one helper, or sends loop on `E2E_DEVICES_MISMATCH` (covered by the list-versus-load test and K4.1 scenario 3).
5. The pending locale/UI WIP in the working tree overlaps K2.2; land or commit it first.
6. The web app has no component test framework, so K1.1, K1.3, K3.2 and K3.3 are verified in a browser.
